# 一页复盘：制度知识库（项目二）

## 遇到的最大困难：外部依赖服务的"慢"与"重"远超预期，且故障形态会伪装

项目二把识别全部外包给项目一的 OCR 服务后，联调期一连串问题都表现为"任务卡住"，
但根因各不相同，逐个排掉才让链路真正跑通：

1. **CPU 争抢型龟速**——扫描件每页 10+ 分钟。排查发现 Docker Desktop 里挂着多套闲置的
   本地开发容器（已运行数天）吃满 CPU，PP-StructureV3 在残血 CPU 上爬行。关停闲置容器后
   速度恢复约 30 倍（10 分钟/页 → 20~60 秒/页）。教训：**性能问题先看整机负载，再怀疑代码**。
2. **队列放大型浪费**——项目一没有任务取消/按内容去重的接口，项目二侧每次重试、每次进程
   重启都会在项目一留下"孤儿任务"，重复烧几十分钟 OCR 还挡住后面的文件。本次靠人工识别
   同 sha 重复并清理疏通。已列入项目一改进建议（按 sha 幂等提交或补取消接口）。
3. **Windows 中文路径坑**——FAISS 的 C++ 文件接口在 Windows 上打不开含中文的 UTF-8 路径
   （仓库目录名就含"制度知识库"），索引落盘直接崩溃。改用 Python 字节流序列化
   （`faiss.serialize_index` → `Path.write_bytes`）彻底绕开。

## 解决方式的共性

三件事的解法其实是同一个：**把"黑盒等待"变成"可观察的事实"**——队列水位接口、
任务库直查、逐步日志，让每一次"卡住"都能在三分钟内定位是哪一层、谁的锅。
这也是为什么心跳租约坚持"判死依据是无心跳而非超时"：判据必须反映"还活着吗"，
而不是"跑了多久"。

## 设计上最值得的两个决定

1. **P1 结果 JSON 整包存档**：重新解析从存档重放（秒级、零 OCR 费用），解析详情、
   错误归因、评测溯源共用同一份事实源；
2. **章节面包屑兜底**：文字层直读路径没有标题块，靠"第X章/附录X"正则从正文恢复章节
   ——原型要求的"目录结构 + 章级出处"在没有 OCR 标题的文档上也能达成。

## 遗留问题

- 扫描件 OCR 会丢条号数字（"第一条"识别成"第条"），影响该类题正确率，评测归因已能
  自动标注为 OCR 错误；
- 拒答阈值 0.55 为经验初值，尚未做区间扫描校准；
- 流程图 VL 描述的交叉校验（节点名 ⊆ OCR 文字）偏保守，复杂图可能被降级。
