# 项目方案：制度知识库（项目二）

提交人：　　　　提交日期：

> 三个项目合计 5 个工作日，本方案按项目二占 **2.5 个工作日**编排。项目一 OCR 服务已具备 HTTP 形态（API + 双 worker + 任务库），本项目直接消费其接口，契约见 `01-OCR流水线/服务/docs/API接口文档.md`。

## 1. 我对需求的理解

1. **一条解析流水线喂全系统**：10 份制度文件三种形态（旧版 .doc、可复制 PDF、扫描/盖章 PDF）全部转 PDF 后经项目一接口解析为结构化块，项目二不另做识别；
2. **问答必须带可验证的出处**：每条回答注明"哪份文件 · 哪个部分（章/条/附录/表格）"，点击落到原文位置——答案与出处分别计分；
3. **答不出就是答不出**：资料里没有的明确回答"没有找到相关规定"，不编造；
4. **表格和流程图是制度的一部分**：问到表中标准、流程图节点也要答对，是解析与检索设计的核心难点；
5. **过程可查、效果可测**：管理员能看到每份文件解析成了什么（解析详情页）；35 题评测集一键运行出正确率；扫描件错题可归因（OCR 错 / 检索错 / 回答错）。

## 2. 需要确认的问题

| 3 | 制度文件后续是否会增删替换 | 索引同步按全自动设计（增删改即时同步），另留手动"重建索引"按钮兜底，两者都做 |

## 3. 总体设计

### 3.1 系统结构与数据流

```
前端 5 屏（照原型）
   │ HTTP / SSE
p2-kb 知识库服务 ── SQLite（kb.db，数据真身）+ FAISS 索引（可再生缓存）+ uploads/crops 文件卷
   │ HTTP（契约已冻结：POST /api/v1/documents 异步 + GET /api/v1/tasks/{id} 轮询）
p1-ocr 识别服务（项目一 · API:8700 + 双 worker + 任务库心跳队列 · PaddleOCR）
```

三条边界：项目一只负责"PDF → 结构化块"；全系统文字识别唯一来源是项目一；SQLite 是真身、FAISS 是缓存——向量同时以 BLOB 存库，索引损坏或换模型时零 API 费用重放重建。

**摄入主路径**：.doc/.docx 先经 LibreOffice 转 PDF（此后只有一条解析路径），提交项目一异步识别 → 轮询至终态 → 结构化结果 JSON **整包存档**——解析详情、重新解析重放、错误归因的唯一事实源。

### 3.2 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 后端 | Python + FastAPI | 与项目一同栈；异步支撑 SSE 流式问答与后台消费循环 |
| 数据库 | SQLite（WAL） | 10 份文件量级单文件零运维；队列复用其条件更新，不需要独立消息队列 |
| 向量检索 | FAISS IndexFlatIP + IDMap | 千级向量毫秒检索；支持按 ID 增量摘除（删除同步索引） |
| 关键词检索 | SQLite FTS5 trigram | 与库同源零依赖；查询不足三字（"印章""差旅"）自动回退 LIKE |
| 部署 | docker-compose 两服务 | p2-kb 与 p1-ocr 分离（重依赖隔离），健康检查保证启动顺序 |

### 3.3 模型选型（全部走 DashScope API，不租 GPU）

| 用途 | 模型 | 理由与备选 |
|---|---|---|
| 向量化 | 通义 embedding（768 维） | 已在真实数据量级验证；备选本地 bge-m3（省 API 费但引入部署依赖） |
| 生成/改写/判分 | qwen flash 档 | 成本低、中文制度文风合适；评测不达标升标准档 |
| 流程图结构描述 | qwen-vl | 仅此一处；与 OCR 文字交叉校验后生效 |

### 3.4 关键组件实现说明

向量管理、DashScope 客户端、任务队列（领取/心跳租约/回收）、RRF 融合、评测骨架等核心组件均为本人独立实现，无第三方黑盒依赖，答辩时可逐行讲述其设计与取舍。

## 4. 关键难点和做法

**难点一：出处精确到"部分"，且点击可达。** 块是检索与出处的一等公民：每块携带文件名、页码、坐标框、类型，并维护**章节面包屑**——解析时跟踪最近标题块，把"第三章""附录 C"写入块元数据，出处统一渲染"文件名 · 章节 · 第 N 页"。点击按块类型分流：正文高亮坐标框、表格渲染 HTML 并高亮命中行、流程图展示裁剪原图。一个块 ID 锁死一切。备选：个别扫描件标题识别失败时面包屑退化为仅页码，不阻塞主流程。

**难点二：表格与流程图可问答。** 表格双粒度分块：每行带表头拼成行影子文本参与检索（问"正高级住宿标准"命中那一行），整表另存一块负责展示；表格 HTML 全程保留。流程图：按坐标框从 PDF 裁图 → 视觉模型生成"节点 + 分支 + 走向"描述，与 OCR 节点文字拼接；**交叉校验**（视觉模型的节点名必须能在 OCR 文字中找到）防幻觉，不过即降级纯文字。备选：视觉模型不可用时全线降级，流程图题凭节点文字仍可部分答对。

**难点三：拒答，不编造。** 双保险前置：检索阶段向量与关键词**两路皆弱**才拒答（关键词精确命中、仅向量分低时不误杀），直接回答"没有找到相关规定"，不调生成；生成阶段提示词三条铁律——只依据资料、必须标引用编号、资料不足必须明说。阈值初值 0.55，评测验证区间 0.45–0.65。

**难点四：长任务队列可靠性（扫描件一份合法跑 5–10 分钟）。** 心跳租约：任务行即租约，领单写持有者与存活时钟，执行期间每 30 秒续约；回收判据"5 分钟无心跳"而非"超时"——慢任务活着永不被误杀，进程崩溃最迟约五分半钟自动重投，累计三次落失败终态。心跳双向闭环：执行者发现租约丢失（行被回收或管理员重置）立即自我取消止损。不做启动清扫——多实例下那会抢走活任务；周期回收幂等，水平扩容无需特殊处理。

**难点五：扫描件答错归因（验收必考）。** 每块落库保留该页识别方式（text_layer/ocr）与 OCR 置信度；评测明细据此把错题归因为"OCR 读错 / 检索没召回 / 检索到了回答错"。

## 5. 数据设计

SQLite 单库七张表（WAL，时间统一 unixepoch 整数）：

| 表 | 要点 |
|---|---|
| documents | 文件名/格式/sha256/页数·表格数·流程图数/superseded_by；队列五字段（状态/持有者/心跳时钟/尝试次数/错误）；项目一返回 JSON 整包存档 |
| chunks | 所属文档/页码/坐标框/块类型（正文·表格行·整表·流程图）/章节面包屑/检索文本/表格 HTML/裁图路径/流程图线性文字与视觉描述/识别方式与置信度/向量 BLOB/FAISS 编号 |
| conversations / messages | 多轮对话上下文 |
| eval_items / eval_runs | 评测题与运行（逐题结果 + 归因 + 配置快照） |

关系：documents 1—N chunks；旧版本经 superseded_by 指向新版，检索默认过滤旧版并在回答末尾提示。

## 7. 怎么证明做好了

**自测矩阵**：10 份文件全量导入就绪；处理中 kill 进程五分半钟内自愈重投；删除文件索引即时同步；重复导入幂等；长文档处理中问答屏仍可流式回答（事件循环未阻塞验证）；新旧版本默认新版并提示。

**评测集**：35 题（正文 15、表格 8、流程图 4、查无 5、新旧版 2、多轮 1），一键运行，LLM 判对错 + 出处比对金标，扫描件错题归因。

**效果指标（预估）**：正文 ≥90%、表格 ≥85%、流程图 ≥70%、查无拒答 ≥95%、出处正确率 ≥90%、平均耗时 ≤5 秒。达不到的项自测报告如实列出并归因。

**现场改动储备**：① 流程图节点高亮；② 出处追加章节全文；③ 检索条数调参对比。
